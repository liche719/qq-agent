# 记忆与召回：整体设计

> 最后更新：2026-11-04
> 目标：**召回率 ≥ 75%**、注入字数 ≤ 800、p90 ≤ 1.5s、每轮成本 ≤ 0.01 元。

## 1. 约束（决定了设计，别先谈技术）

| 约束 | 数值 | 影响 |
|---|---|---|
| 单用户记忆量 | 349 条（ACTIVE 266 / EXPIRED 19 / COMPLETED 13），未来几千 | **不需要独立向量数据库**，pgvector 够 |
| 检索延迟 | p50 0.68s / p90 1.4s | 每层都要有预算和跳过条件 |
| 成本 | 每轮 0.01 元级 | 候选少就别精排；能本地算的别调模型 |
| 正确性优先级 | **记忆不丢 > 找得准 > 快** | 写入路径比检索路径更重要 |

## 2. 四层漏斗

```
写入层：对话 → 提取 → 去重/合并 → 落库（必须可追溯 source_message_ids）
   ↓
存储层：memory（长期事实） / memory_fact（槽位+失效链） / conversation_memory（原文证据）
   ↓
检索层：结构过滤 → 多路召回 → 并集去重 → rerank 精排 → 断层截断 → 预算装配
   ↓
观测层：召回评测（题库） · 成本 · 延迟
```

## 3. 检索层设计（核心）

### 3.1 三路召回，各管一段

| 路 | 负责 | 状态 |
|---|---|---|
| **结构化过滤** | userId / kind / 时间窗口 | ✅ 在用（第一道闸） |
| **稠密向量**（pgvector） | 语义相近，换说法也能找到 | ✅ 在用（当前唯一排序依据） |
| **BM25**（jieba，应用内存） | 字眼对上：恩儿 / 6e206 / 521 | 🟡 代码保留，**当前关闭**（实测对现有题库无收益，见 §6） |
| **查询改写** | 把"上次那件事"补成具体词 | ✅ 在用（2026-11-04） |

**编号类（6e206、ERR_502）另走精确匹配**：这类要求一字不差。

### 3.2 排序：实测过 RRF 和 rerank，最后都去掉了

同题库（250 题自动生成、固定抽样）实测：

| 配置 | 召回率 | 平均注入字数 |
|---|---|---|
| 向量 + **rerank** | **53.6%** | 1335 |
| 向量 + BM25 并集 + rerank | 52.8% | 2797 |
| 向量 + BM25 + **RRF**（无 rerank） | 27.6% | 2298 |
| 向量 + BM25 并集（无 rerank） | 52.4% | 2772 |
| **向量 + 查询改写（当前）** | 53.6%（改写效果需真实对话验证） | 1335 |

**三个结论**：

1. **RRF 在这里有害**：两路候选高度重叠、RRF 分数是 `1/61` 量级，
   原有的阈值/截断全部失效，结果取满上限、语义被抹平（TASK 类掉到 15%）。
2. **并集不是融合**：把 BM25 候选直接堆进来，rerank 要在更嘈杂的池子里挑，
   反而把向量已挑中的挤掉（53.6% → 52.8%，字数翻倍）。
3. **rerank 有收益但成本不可持续**：实测 3632 次调用烧光免费额度，每轮约 0.008 元；
   而 68% 的未命中是**纯指代问题**，精排根本无从下手——钱花在了错误的地方。

**所以最终形态**：向量负责排序，BM25 保留代码但关闭，rerank 移除，
把力气花在**查询改写**上（成本约为 rerank 的四十分之一）。

### 3.3 查询改写：针对那 68%

`MemoryQueryRewriter`：指代型问题（"上次那件事怎么样了"）用最近 3 轮对话补成
具体查询（"恩儿 10月31号 不回消息"）再检索。

- **只在追问时触发**：含「上次/之前/那次/那件事/刚才/后来」，或"短句 + 疑问词"
- **不触发**：夸奖、附和、陈述（踩过坑：`哈哈记得真好` 曾被当成指代型改写，白花一次调用）
- 失败一律退回原句

### 3.3.1 断层截断（rerank 时代的设计，保留说明）

```
按分数从高到低取：
  ① 最多 topN 条
  ② 相邻分数差 > gap(0.15) 立刻停
  ③ 绝对分 < floor(0.30) 一律不要
```

rerank 移除后，这套阈值**不再生效**（向量相似度和 RRF 分数不在同一量纲），
截断交回字数预算（`coreMaxChars` / `workMaxChars`）。

### 3.4 每一层都要有兜底

| 层 | 挂了怎么办 |
|---|---|
| rerank | 退回并集原顺序（只是不够准，不会崩） |
| BM25 索引 | 退回纯向量 |
| 向量（embedding 未配） | 退回字面 + 画像 |
| 全部失败 | 注入"（暂无）"，不阻塞对话 |

## 4. 规模演进（什么时候换什么）

| 规模 | 方案 |
|---|---|
| 现在（<1 万条） | 内存 BM25 + pgvector + rerank |
| 单用户 >5 万条 | BM25 挪到 PG（zhparser），别再全内存 |
| 多实例 | 索引/缓存全 Redis 化 |
| >100 万条 | 才考虑独立检索服务 |

**关键**：`LexicalSearcher` 做成接口，换实现不改调用方；**单用户记忆数超过 5 万要告警**，让系统提醒该换了。

## 5. 明确不做

| 不做 | 为什么 |
|---|---|
| 引入向量数据库（Milvus/Qdrant） | 349 条，pgvector 够；多一个服务多一个故障面 |
| RRF 叠在 rerank 前面 | 排序叠两层互相污染 |
| 每次全量重排所有记忆 | O(n)，几千条就慢 |
| 多 Agent 协作 | 单人陪伴场景用不上 |

## 6. 当前实测（2026-11-04，250 题自动题库）

| 指标 | 数值 |
|---|---|
| 召回率 | **53.0%**（PROFILE 55.7 / TASK 44.9 / EXPERIENCE 57.4） |
| 平均注入 | 1168 字 |
| p50 / p90 | 677ms / 918ms |

**未命中的构成**（145 条）：
- 68% 是**纯指代/情绪**（"我上次说的你还清楚吧""我那晚到底在烦啥"）→ 字面检索无效
- 31% 有字面重叠 → BM25 能救
- 0% 编号类（题库生成指令把它消掉了，需重造题库才能测准）

## 7. 从 53% 到 75% 怎么走

| 步骤 | 手段 | 预期 |
|---|---|---|
| 1 | 修 BM25 索引 bug（现在只建了 3 条，等于没生效） | +5~10% |
| 2 | **查询改写**：指代型问题（"上次那件事"）用最近上下文补全成具体查询 | **+10~15%（关键）** |
| 3 | 时间感知加权：查到"那天/上周"时给对应时间窗记忆加分 | +3~5% |
| 4 | 扩大候选池（K 从 30 提到 50）+ rerank 收紧 | +2~3% |
| 5 | 题库补编号类题目，重测 | 校准 |

> **75% 的瓶颈不在检索算法，在"纯指代问题"占 68%。** 不解决指代，加多少路召回都到不了 75%。

## 8. 验收标准

| 指标 | 目标 |
|---|---|
| 召回率（250 题） | **≥ 75%** |
| 平均注入字数 | ≤ 800 |
| p90 延迟 | ≤ 1.5s |
| 每轮记忆成本 | ≤ 0.01 元 |
| 重启后 | 上下文/媒体/告警状态不丢（Redis） |
