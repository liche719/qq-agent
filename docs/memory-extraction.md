# 记忆是怎么工作的（现状一页纸 · 2026-09-14）

> 这份文档回答四个问题：**什么时候写记忆、写什么不写什么、有哪些开关、花多少钱**。
> 起因是 2026-09-14 用户说「感觉越弄越乱」——那天同一条线改了 5 次方向，其中「记忆归纳」上线后又整块删除。
> 这里把现状、被否掉的方案和踩过的坑一次说清，以后不用再翻聊天记录。

## 0. 一句话现状

**对话结束后异步跑一次「记忆提取」，把值得长期保留的信息写进三类记忆（核心 / 中期 / 情景）；
课表这类会变的信息一律不记；"归纳"这条路试过、不合格、已删除。**

## 1. 什么时候写（触发）

```
用户发消息 → 应用照常回复（记忆不在这条链路上，不影响首字延迟）
          → 静默 45 秒（用户继续说话就一直往后推，最多推到 150 秒）→ 跑一次「记忆提取」
```

- 参数：`memory.extraction-window-seconds`（默认 45）、`memory.extraction-max-delay-seconds`（默认 150）。
- **为什么不是每轮一次**：3 秒窗口时，"两条消息间隔超过 3 秒"就会各触发一次提取。实测连发 3 条消息 → 3 次提取、
  三次输入窗口互相重叠（prompt 836 → 895 → 949）。改成 45 秒静默后同样的 3 条消息 → **1 次提取**。
- **提取前还有一道门槛**（`MemoryExtractor.worthExtracting`）：窗口里没有"实质内容"就整个跳过——
  去标点后 ≥5 个字、或含数字、或含「我/咱」。所以「好」「在吗」「嗯嗯」这类不再白跑一次（带思考）的模型调用。
  **跳过不是漏记**：提取窗口是"最近 20 轮"，用户下一句有内容时会把这些短句一起带进去。

## 2. 写什么、不写什么（规则）

提取器（`MemoryExtractor`）一次调用产出的候选类型：`episodes`（情景）、`newWorkItems`（中期）、
`coreCandidates`（核心）、`coreUpdates`/`workConflicts`（修正已有）、`completedWorkItems`（完成）、`duplicates`（重复）。

**必须遵守的几条硬规则**（都在提示词里写死）：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 只能依据 **user 角色**的明确陈述；assistant 的话、工具结果、网页、推测都不能成为记忆 | 防幻觉 |
| 12 | **课表、教室号/上课地点、第几节课的时间、临时日程、一次性数字**（今天学了几小时、几点下课）→ **一律不记**（核心/中期/情景都不写） | 这些"每周都在变"，记下来必然变成错信息。要看就现场读用户保存的课表图 |
| 13 | **只有用户说「记一下/记住/以后都这样」才记**；你从图片里自己看出来的事实不入库 | 同上；也避免"它自己认定" |
| 6 | 与已有核心记忆讲同一件事时**必须写 coreUpdates**，不许新增平行的条目 | 治"旧事实还留着" |

> 规则 12/13 是 2026-09-14 加的。加之前库里躺着一批课表记忆（`晚上上课地点是8B304.305，必须记住`、
> `第1-2节课的下课时间是10:10`、`课表节次时间…`），而用户后来用截图纠正过教室号（7B-301），**那条更正当年没进库**——
> 因为当时的规则 1「只能依据 user 明确陈述」把"你从图片核对出来的事实"也挡住了。
> 用户 2026-09-14 的决定是：**课表类干脆不记，每次看图**，所以没有再实现"允许记录图片核对结果"。

## 3. 冲突/过期怎么处理（两层）

1. **确定性兜底**（零成本）：`MemoryTextSimilarity` 算字符二元组 Jaccard，新候选与已有核心记忆相似度 ≥0.72 →
   走 `CoreMemoryService.replaceFromExtraction`：**旧行 status=SUPERSEDED（不删除）、写变更日志、新建替代行**。
2. **第二次小调用**（`MemoryExtractor.reconcileCoreWithModel`）：字面不像、但可能是"同一件事换了个说法"时，
   问模型一次"这条新事实是不是已有某条的新版本？"（只回编号）。
   - **为什么必须有这一层**：实测「考研数学目标分是130」被改写成「用户在考研中设定的数学目标分数为140分，希望冲刺更高分数」，
     字面相似度只有 ~0.3，兜底抓不到；线上验证靠这次小调用才把 130 那条置成 SUPERSEDED。
   - 这就是 Mem0 那套「抽取」与「与已有记忆比对」分两次调用的最小版本。

## 4. 开关一览（记忆相关）

| 开关 | 默认 | 作用 |
|---|---|---|
| `MEMORY_EXTRACTION_WINDOW_SECONDS` | 45 | 静默多久算"聊完一轮" |
| `MEMORY_EXTRACTION_MAX_DELAY_SECONDS` | 150 | 一直被推时的最长等待（防止一直不触发） |
| `MEMORY_EXTRACTION_RECENT_TURNS` | 20 | 提取时看最近多少轮 |
| `MEMORY_MIN_CONFIDENCE` | 60 | 低于这个置信度不写 |
| `MEMORY_DEDUP_THRESHOLD` | 0.8 | 与已有记忆重复度超过它就不新增 |
| `LLM_MAX_TOKENS_STRUCTURED` | 4096 | 结构化调用（提取/提醒/排程/归档）的输出上限，**思考 token 也算在内** |
| `THINKING_DAILY_LIMIT_PER_USER` | 5 | `thinkDeeper` 升档的每日额度 |

## 6. 被否掉的方案（别再走一遍）

### 6.1 「按场景开关深度思考」——已删除
实测这个模型（`deepseek-v4-flash-vision-exp`）**默认就在思考**，唯一有效的关闭方式是 `thinking:{"type":"disabled"}`。
一度只对 `extract`/`schedule_parse`/短寒暄关掉，但用户体感是"省电档让它显得变傻"，2026-09-14 **整块删除**（含省电档
和 `DialogModeDecider`），现在全部场景都按模型默认思考。历史实测数据留在 `docs/llm-call-modes.md`。

### 6.2 「每天一次记忆归纳（consolidation）」——上线当天删除
思路来自业界（ChatGPT 的后台 dreaming、斯坦福 Generative Agents 的 reflection）：把零碎记忆归纳成少量高层记忆。
**首版实测不合格，三个硬伤**：

1. **不是归纳，是拼接**：提示词要求"不许丢信息 + 必须保留全部数字" → 模型直接把两条原文用「；」连起来
   （「用户是助手的开发者；**用户自称是**助手的开发者。」）。要"归纳"就得允许改写，要"不丢信息"就逼它拼接——规则自相矛盾。
2. **额度被思考吃光**：23 条记忆的归纳，`completionTokens=16384 reasoningTokens=16384`，JSON 一个字没出；
   单次 46~55 秒。加额度到 16384 仍然被吃满。
3. **`replaces` 对不上原文就退化成"新增"**：库里出现大量重复条目（同一句出现 3 次 ACTIVE），
   而且每隔一轮就"合并→再拆开"，来回折腾。

**代价（如实记账）**：20 次调用、输入 22,482 token、**输出 189,354 token（多数是思考）**、6 次撞上限、产出全为零；
同期真正干活的 `extract` 34 次输出合计 19,662 token —— **一次没想清楚的实验烧掉了当天全部记忆提取成本的 9.6 倍**。

后续离线评测（在用户真实记忆上、只读）给了两条**可用的**结论：
- **自由归纳**（让模型在 23 条里自己找重复并写合并文本）：即使允许改写，成本仍是 ~1 万思考 token，且只挑 3 组就交差。
- **两段式**（程序算相似簇 / 或让模型只回编号对，再逐对写合并文本）：找对 `pairs` 用 5,219 tok，
  逐对写合并文本每对 1.2k~2.4k tok，合并质量正常（去重且数字不丢）——**但收益只是"少几条重复"**，
  用户 2026-09-14 的判断是优先做别的（写入正确性 / 画像），所以两段式也**没有实现**。

### 6.3 「当前画像」——只做了离线评测，未实现
把核心+中期记忆+备考计划喂进去，产出一段 ≤200 字的"当前画像"注入对话 prompt 开头。
离线 3 次实测：163/183/187 字、思考 0~1247 token、1~7 秒、没把课表细节写进去（规则约束有效）。
**没上线的原因**：它治不了"记错了"（陈旧断言仍在核心记忆里，照旧被注入），用户选择先做写入正确性（规则 12/13）。

## 7. 已知问题（还没做的）

1. **存量里那条错的教室号还在**：`晚上上课地点是8B304.305，必须记住` 仍为 ACTIVE，而截图上是 7B-301。
   用户 2026-09-14 明确选择**暂时不动存量**（改法：置 SUPERSEDED + 保留旧行 + 快照可回滚）。
2. **它可能嘴上说"记住了"但实际不存**：课表类按规则不记，但对话侧一度仍会回「记下了」。
   已加提示词第 25 条（不许承诺做不到的事），**上线后需在真实对话里复验一次**。
3. **没有画像层**：核心记忆是一堆平铺事实，没有"他是谁/当前主线"的汇总（见 6.3）。
4. 记忆检索仍是"全量注入核心+按关键词取中期"，不是向量检索；库小的时候够用。

## 9. 审计补上了"落库"这一半（2026-10-09）

**改了之前的盲区**：`memory_extraction_run` 里只有 `verdict_json`（模型**提议**了多少条），
而 `written_ids` 从建表起就被 `MemoryExtractor` **硬编码传了 null**——所以"提议 5 条为什么只落 1 条"
这个问题**从来没被回答过**（这也是 2026-10-08 差点误判成"提取花了 1.15 元什么都没写"的原因）。

**现在怎么记的**：`runSafely(userId, 操作名, Runnable)` 是**所有写入唯一的收口点**，
在它里面记一笔就全覆盖（不用改 6 个 applyXxx 的签名和 14 个调用点）。计数用 ThreadLocal 携带，
`apply()` 里 set、finally 里 remove——和 `LlmScenario.CURRENT` 同一套用法。
写失败记成 `失败·操作名`，这样"没写"和"写失败被吞了"分得清。

**口径（重要，别误读）**：

- 计数是**写操作的次数**。每个候选各记一次，所以 `新增情景记忆=1` 就是**真写了 1 条**。
- **批量操作记的是"跑了一次"，不是影响行数**。例：`过期工作记忆=1` 只表示那次过期清理执行了，
  **不代表过期了 1 条**（`expireDueMemories()` 返回 void，拿不到行数）。
- 事实层额外给一行精确的 `事实条数=N`（`factService.apply(...)` 有返回值），
  所以"candidates 里有多少被去重挡掉"看得出来。
- 空串 = 这次一条都没写成；**2026-10-09 之前的行是 NULL（历史缺失，不能用来做对比）**。
- 落库**只记计数、不记 id**：写入走的是 `Runnable` lambda，拿不到自增 id；要 id 得把 14 个调用点
  改成带返回值。而"提议 vs 落库"这个对照**只要计数就够**，所以先这样。
- `runs()` 接口（`GET /api/admin/memory/runs`）已经把它作为 `written` 字段返回。
  **前端目前没有消费这个接口**，所以这次没动前端。

**第一次真实数据（2026-10-08 14:11 手动触发）**：

```
提议[core=0 work=0 episode=1 updates=0 completed=0 duplicates=9 facts=0]
落库[新增情景记忆=1,过期工作记忆=1]
```

提议 1 条 episode → 真落 1 条，对照成立。
**顺带一个值得盯的信号**：44 轮窗口里模型提议 10 条、其中 **9 条判成 duplicates**——
说明窗口和"已经处理过的内容"重叠很大。如果连续几次都这样，那"窗口能不能缩短"就值得算一笔账。

## 10. `memory_extraction_run` 的 token/钱是"整个进程"的，不是这一次提取的（2026-10-09 查清）

**症状**：`prompt_tokens` 在 **7015 ~ 58847** 之间跳（8 倍），但窗口字符数一直只有 5000~7800。
比值 `prompt_tokens / window_chars` 平时稳在 **1.2~1.4**，异常的三次都在 **10-05 晚上**（3.24 / 7.11 / 2.59）。

**根因**：`MemoryExtractionAudit.begin()` 取的是 `LlmUsageRecorder` / `LlmSpendMeter` 的
**进程内全局计数器快照**，`finish()` 拿差值。这两个是全局单例（`LongAdder`）——
所以**提取那几十秒里发生的任何别的 LLM 调用（用户正在聊天）都会被算进这一行**。

**铁证**（`llm_call_audit` 里同一时刻的逐次记录）：审计说 10-05 22:28 那次 `prompt=35388`，
真实发生的是 `22:28:04 extract prompt=7370` + 三次小 extract（725/741/759）
+ 22:27:04~22:27:35 三次 dialog（12155/11715/14078）——**加起来正好是三万多**。

**所以**：**大提取调用的 prompt 一直稳定在 7000~7900 token，从来没膨胀过。**
之前"prompt 会涨到 58847"的结论作废。

**怎么读这两张表**：

| 想知道什么 | 看哪 |
|---|---|
| **一次提取自己花了多少** | `llm_call_audit` where `scenario='extract'`（现在最准） |
| 一个"提取 run"总共花了多少（含它触发的 N 次小判定） | 同上按时间窗聚合；`memory_extraction_run.cost_yuan` 只当**上界** |
| 那次进程整体花了多少 | `memory_extraction_run.cost_yuan`（但它含并发对话） |

**一个 run ≠ 一次 LLM 调用**：一次提取 = **1 次大调用**（带完整窗口，7000+ token）
**+ N 次小调用**（"事实关系判定" `MemoryFactService.classify` 也挂在 `LlmScenario.EXTRACT` 上，
725~885 token，一次 0.001 元上下）。小调用把 `extract` 的平均 prompt 拉到了 4498。

**真实成本（`llm_call_audit`，2026-09-23 ~ 10-08，15 天）**：

| 场景 | 次数 | 花费 | 平均 prompt | 平均输出 | 缓存命中 |
|---|---|---|---|---|---|
| dialog | 135 | 0.5880 元 | 11934 | 320 | **82.1%** |
| extract | 25 | **0.5702 元** | 4498 | 3496 | **5.5%** |
| reminder_parse | 1 | 0.0030 元 | 510 | 253 | 0% |

→ 提取 **0.038 元/天**、对话 0.039 元/天，整机约 **0.08 元/天 ≈ 2.4 元/月**。
**本文件里此前出现过的"提取 0.055 元/天""0.15~0.3 元/天"都作废**，那两次都被这个计量口径骗了。

**还没做的**：把审计的计量口径修准（让 `cost_yuan` 只算这次提取自己的调用）。
两条路：① 让 `LlmUsageRecorder`/`LlmCostLedger` 额外维护一份 **ThreadLocal** 计数，
提取在自己的线程上同步跑，前后差值就只含自己的调用；② `finish()` 里直接查
`llm_call_audit where scenario='extract' and created_at in [start, now]`。
①更彻底但要动全局账本（对话预算也用它），②只动审计、但要防两个提取 run 重叠时重复计数。
**在定下来之前，按上表读 `llm_call_audit`。**

## 11. 「更新/取代」路径**已受控验证通过**（2026-10-09，这套记忆系统最关键的一次验证）

**背景**：事实层（subject/predicate/object）是专门为"会变的信息只改一格"建的，
但截至 10-08 它在生产里**一次都没触发过**——`memory_fact` 28 条全是 ACTIVE、0 条 SUPERSEDED，
25 次提取里 `updates` 只有 2 次非零。**"有代码、零流量"是这里最大的风险**：
万一不生效，用户说"教室改成 305"，库里会同时留着 303 和 305，下次回答拿旧的糊弄他——
正好踩在"记忆不丢失/不能记错"这条第一优先级上。

**实验方式**（不污染用户真实聊天记录）：
往 `conversation_memory` 注入一条 user 消息「第一节课的教室改成 9B305」
（靶子是库里已有的 `id=24 第一节课·教室 → 教室 = 9B201`），触发一次提取，观察，然后回滚。

**结果——完全按设计工作**：

```
id=24 | SUPERSEDED | 第一节课·教室 → 教室 = 9B201 | sup_by=32      ← 旧值被取代，**没有删行**
id=32 | ACTIVE     | 第一节课·教室 → 教室 = 9B305 | sup_by=NULL    ← 新值生效

memory_change_log:
  449 | FACT | SUPERSEDE | target=24 | 主调用判定：同一属性被改写
        before=第一节课的教室是9B201 → after=第一节课的教室改成9B305
  450 | FACT | ADD       | target=32
```

四条结论：
1. **改写而不是新增平行行** —— 同一 subject + 同一 predicate 被正确取代。
2. **旧行保留**、`superseded_by` 指向新行 —— 能回溯"以前是什么"。
3. **由主调用判定**（提示词第 15 条那套 fact cards + relation/targetSubject），
   **没有退回**"向量召回 + 每次一条小判定"的兜底路径 —— 说明那条省钱的设计也真的在工作。
4. **相似度阈值（0.72）没有把它误判成 duplicates** 而干脆不写。

**回滚**：注入的消息、新事实行、测试产生的变更留痕、测试的审计行全部删除；
`id=24` 精确还原（status/object/superseded_by/updated_at 都还原）。
**保留**了这次一并提取出的 2 条**真实**记忆（用户童年那段）——那不该删，删了就是真的丢记忆。

**顺带一个实用结论**：存量里那条错的教室号（`周二晚上·课 → 教室 = 8B304,8B305`，
而截图上是 7B-301）**现在有解了**：不需要手工改库，只要在 QQ 里说一句
「周二晚上的课教室是 7B-301」，取代路径自己会处理（§5 的"存量清理"不用再手工做）。
