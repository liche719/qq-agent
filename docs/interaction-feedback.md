# 交互反馈：进度条、语音时机、轮内注入、按需工具（2026-10-22）

这一批全是为了同一个目标：**他在 QQ 里能看清"笨鱼在干什么"，而且笨鱼说的和做的一致**。
按主题记结论、踩过的坑、以及"为什么是现在这样"，避免下次又试错一遍。

## 1. 工具进度条（一条流式消息，不撤回）

- **形态**：一条 QQ 流式消息（`stream_messages`，`input_mode=replace`），每开始一个工具就追加一行：
  `· 看B站视频：给大肥鱼量体重`。行数上限 12，同一个工具只报一次；`sayToUser`/`sendVoice` 不算工具，不显示。
- **为什么不撤回**：撤回不退还被动回复额度（发送时就扣了），删了只是把信息藏起来。留着当"这一轮干了什么"的记录。
- **为什么必须用流式消息**：普通消息一条只能一行，几条就占几次额度；流式消息更新多少次都只算 **1 条**。
- **为什么流式消息删不掉**：平台的流式消息 id 是 UUID，调 `DELETE /v2/users/{openid}/messages/{id}` 返回
  `40061001 请求参数无效`；普通消息的 `ROBOT1.0_...` id 撤回是 200。这条实测过，别再试。
- **收尾**：这一轮结束时发一帧 `input_state=10` 把气泡定格。若答案也开了流式，两者共用同一条入站
  `msg_id` 会撞 `40034019 流式引导已经结束`——所以**答案流式现在关着**（`AGENT_REPLY_SPLIT_DISABLE_STREAM=true`）。
- **心跳**：`SLOW_EXTERNAL` 工具跑超过 30 秒，后台线程每 30 秒往同一条进度消息追加"还在…"（最多 3 次）。
  实现是 `AgentLoop.startProgressHeartbeat`：ThreadLocal 拿不到通道，所以 `TurnProgress.progressSender()`
  把通道本身交出去，由定时线程调用——`QqChannel.progressLine` 内部是并发安全的。

## 2. 语音：什么时候发由模型决定，但必须说到做到

- 工具签名：`sendVoice(text, atEnd?)`。
  - `atEnd` 省略 → **调用这一刻就发**（默认）；
  - `atEnd=true` → 合成后暂存（`VoiceOutbox`），等这一轮文字发完再发。
- 触发规则：他说「先发语音 / 马上发 / 现在就发」→ 省略；说「最后再发 / 等你说完再发」→ `true`；**不确定就省略**
  （提前比延后更容易让他等错）。曾经把「先给我发语音」判成延后，被当场纠正过。
- **不许言不由衷**：工具返回分两种说辞——即发的说"就是现在，别再补一句稍后发你"；延后的说"会在这一轮文字之后发"。
- **定时任务里的坑**：定时任务用合成消息（`InboundMessage.text(...)`），默认 channel 是 `"simulator"`，
  生产没有这个通道 → `ToolStatusService.sendVoice` 找不到通道，**静默返回 false**（连日志都没有）。
  现在 `ScheduledTaskService` 按 `wechat.channel.mode` 传真实通道，并且合成 msg_id 被平台拒时
  自动改投**主动消息**（不带 msg_id）；同步任务末尾还会 `flushDeferredVoice` 补发暂存的语音。
- **TTS 不稳**：阿里云 qwen3-tts-flash 偶尔 30 秒不返回。现在超时 **45 秒 + 重试一次**，仍失败就如实说没发成。

## 3. 轮内注入（他在笨鱼干活时插话）

- 一轮在跑时新消息不再排新任务，而是进 `TurnSteering` 队列；`AgentLoop` 在**每次调模型前**取一次，
  作为一条 user 消息追加："（你干活时他又发来：…。先把手上这步收尾，再按他的话调整）"。
- 每轮最多注入 2 次、待注入队列最多 3 批；轮末没赶上的由 `resumePendingBatches` 合并成下一轮。
- 注入的消息会写进 `conversation_memory`（独立 `event_key`），否则第二天查不到"他中途补的那句"。
- 实测：「停」在他读视频时发进来，1 秒后被注入，那一轮真的停了。

## 4. 工具按需解锁（渐进式披露）

- 默认只发**核心工具 34 个**（说话/语音/画图/搜索/网页/文件/B站三件套/媒体记忆/记忆事实/聊天记录/提醒/后台任务
  + `discoverTools` 本身），其余 **30 个**（自主模块 22、定时任务 5、面试 3）靠 `discoverTools` 解锁。
  目的：每轮少发约 2.8k token 的 schema（6k → 3.2k），第一跳首字更快。
- 解锁是**本轮有效**：`ToolDiscovery` 是 ThreadLocal，`AgentLoop` 每轮开始清空。
- 搜索匹配按**片段**（3–4 字窗口）而不是整串——模型爱写整句（「看一看我自己工作区里的文件列表」），
  整串比对会连失败两次。
- 回滚开关：`AGENT_TOOLS_PROGRESSIVE=false`。

## 5. 搜索条数与结果长度

- `searchWeb` / `searchLatestWeb` / `searchVerifiedWeb` 都多了一个可选 `count`：默认 **6**、最多 **15**。
  查单个事实 3–5 条，汇总/比价 10–15 条。
- 原文摘录（deep read）总长封顶 **3000 字**：之前 3 篇 × 每篇几千字，一次搜索就能顶到 8000 字上限，白烧 token。
- 回答长度约束写在**工具结果里**（"只讲最要紧的 2–3 条，200 字以内"）——系统提示词里写 80 字压不住。

## 6. 消息合并与启动时延

- 纯文字窗口 **300ms**（以前 2.5s，太慢）；带图/视频仍等 5 秒，把连续上传的几张图合成一轮。
- `queueWaitMs` 现在只算"派发 → 真正开始"这一段；以前用消息时间戳（= 平台发送时间），
  会把 QQ 投递延迟（0.8–5 秒）也算进去，排查时误导过。
