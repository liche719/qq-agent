# qq-agent 重构一页纸（2026-10-27 ~ 28）

> 一页纸结论：把两个 2000/1500 行的"上帝类"拆成 **20 个职责单一的类**，
> 全程 **25 个测试类 / 80 个用例** 守着，**每一步都能单独回滚**，
> 且**没有一次靠"看起来对"收工**——每个改动都要么有单测、要么有生产日志。

## 一、做了什么

| 原来 | 现在 | 解决的问题 |
|---|---|---|
| `QqChannel` 2036 行（收发/面板/进度/额度/卡片/引用解析混在一起） | **1778 行** + 12 个专职类 | 发消息只有一个 HTTP 出口（`QqMessageSender`） |
| `AgentLoop` 1523 行（对话/计划/反思/工具编排/埋点/进度） | **1338 行** + 4 个类 | 工具执行独立成 `ToolRoundExecutor`，可并行、可测 |
| `AgentOrchestrator` 824 行 | 822 行 + 2 个类 | 回复来源与交付收尾各自成类 |
| `MemoryBackupJob` 861 行 | **816 行** + `BackupArchives` | 打包/改写备份包可用临时目录测 |
| 16 个文件各写一份 `clip`（10 种不同实现） | 13 份收敛到 `support/Texts`，3 份**刻意保留**并写明原因 | 消除"看起来一样、行为不同"的隐性差异 |

## 二、几个能讲的设计取舍

1. **并行执行只给"只读 + FAST"**：`ToolRoundExecutor` 按 `allowParallel ∧ 无副作用 ∧ 非破坏性` 分段，
   有副作用的强制串行。默认值 `allowParallel=true`，只看这个字段会把"建提醒"也并起来。
2. **工具结果必须按请求顺序回填**：并行执行后仍按原顺序写回上下文——顺序错位比慢更糟，
   模型会拿到"先读 A 的结果挂在 B 名下"。
3. **发送链路失败要分三类**：4xx 明确拒收（可重发）、连接没建起来（可重发）、
   **读超时（结果未知，不能重发）**。判错就是用户收两条或收不到。
4. **状态类必须一次替换到底**：抽 `QqReplyWindow` 时试过"只改一半调用"，立刻出现"记得住但查不到"的双份状态，
   当场回滚重做。
5. **静默失败比报错更糟**：一处"只有历史媒体标记就跳过"的守卫，让用户发的消息**完全没有回复**，
   而监控全绿（site 200 / 0 ERROR）。改成"如实说没收到内容"。

## 三、怎么保证没搞坏

| 手段 | 内容 |
|---|---|
| 单测 | 25 个类 / 80 个用例，**部署前必跑，红了阻断发布** |
| 逐步部署 | 一步一提交，部署后 6 项验证（镜像 tag / `site=200` / Started / 0 ERROR / 64 工具 / 统计接口） |
| 回滚 | 服务器装了一键脚本 `qq-agent-rollback <tag>`（自动健康检查、失败自动切回），**实测演练过两次** |
| 生产自证 | 用告警测试接口触发真实发送，验证新类真的在线上路径上（日志类名 `[QqOutbound]`） |
| 静态等价核查 | 搬运前后的方法做归一化 diff，确认差异只有"依赖注入"这一层 |

## 四、验证不到位的地方（如实说）

**被动回复分支（带 `msg_id`、1 小时窗口判定）尚未在真机跑过。**
代码是逐字搬的、单测覆盖了四条判据、同类主动分支已生产验证，但"真的能发出去"只能由一条真实消息证明。
在没有真实流量的情况下，我**没有**把它标记为完成。

## 六、覆盖率（2026-10-28 用 JaCoCo 实测）

只统计本次拆出来的 21 个类，跑 CI 那 118 个用例：

| 覆盖率 | 类 |
|---|---|
| **100%** | `QqMessages`、`QqNumbers`、`QqPanels`、`QqSendErrors`、`Numbers` |
| 94~98% | `QqTexts`、`ToolRoundExecutor`、`BackupArchives`、`ReplyDelivery` |
| 77~85% | `QqOutbound`、`ReplySources`、`Texts`、`QqReplyWindow` |
| 33~67% | `QqProgressSessions`、`ProgressNarrator`、`PlanCoordinator` |
| 0~23% | `QqPanelSetup`、`QqProgressFrames`（都是纯 HTTP，只能靠真机）、`QqQuotas`、`TurnMetrics`、`QqMessageSender` |

**合计 658 行、覆盖 412 行 = 63%。**

0% 的那几个**不是漏测**，而是它们只做 HTTP 调用（面板注册、进度帧发送）或只打印日志（`TurnMetrics`），
单测价值低——它们的正确性由生产日志验证（`command panel already exists`、`工具进度（第 N 行）`）。

**没有设覆盖率门槛**：仓库里还有 15 个历史遗留的过期断言（见 `refactor.md`），
卡覆盖率会让历史债挡住每一次发布。等那批测试清干净再谈门槛。
