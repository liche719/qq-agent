## 0. 一句话

把"时间驱动的后台提取"改成**轮次驱动 + 时间兜底**；把"只新增事实"改成**新增 + 补充 + 纠正**（可变更新的记忆）；用一个**向量召回**替掉现在的字面相似度，来做"新记忆 vs 旧记忆"的矛盾/补充判断；并明确**一条记忆的粒度**是"实体卡片"，不是"一句话塞多件事"。

## 0.5 已定决策（2026-09-17 用户拍板）

| 问题 | 选择 | 落地方式 |
|---|---|---|
| 向量库 | **A：MySQL 存向量 + 应用内检索，抽接口** | 新增 `MemoryVectorStore` 接口（`upsert/search/delete/rebuild`）+ MySQL 表 `memory_vector` + 启动加载进内存做点积；换 pgvector 只换实现 |
| embedding | **阿里云百炼（qwen3 系列向量模型 / text-embedding-v4，0.0005 元/千 token）** | key 只放服务器 `.env`；**必须有降级路径**（provider 不可用 → 退回字面/关键词召回，且降级时只新增、不做合并） |
| 记忆粒度 | **一条一句事实（Mem0 默认）** | 见 §2.3 的定稿：存原子、**注入时按 subject 聚合**、按 `subject+predicate` 精确更新 |
| 时间兜底 | **6 小时**（见 §2.4 的算账） | 频率高一点、反馈快；多花的钱 < 1 元/月 |
| 两套真相 | **一套事实 + 来源层级**（§5） | 资料（图片/文件）抽出的事实标 `DOC`＝基础信息；用户补充/纠正标 `USER`；冲突时 `USER > DOC > AUTO`，同级取最新 |

### 2.4 6 小时 vs 12 小时：算给你看（结论：选 6 小时）

**先排除 embedding 成本**（它不是决策变量）：

| 项 | 量 | 钱 |
|---|---|---|
| 每次提取的向量化 | ≈10 条候选 × 40 token + 10 次检索 query × 50 token ≈ **900 token** | 0.00045 元 |
| 每天（提取 2~6 次） | ≈2k~5.5k token | **0.001~0.003 元/天 ≈ 0.03~0.09 元/月** |

**真正的差额在"兜底触发"多出来的提取调用**（每次提取实测 0.002~0.014 元）：

| 兜底 | 每天最多兜底次数 | 相比 12h 多花 | 体感 |
|---|---|---|---|
| 12 小时 | 2 | — | 当天说的事可能第二天才入库 |
| **6 小时** | 4 | **≤2 次/天 ≈ 0.004~0.028 元/天 ≈ 0.1~0.8 元/月** | 最多 6 小时入库 |

**而且这 0.1~0.8 元还是上限**：兜底触发的那一轮如果整窗都是"问课表/设提醒/元问题"，会被已上线的**事务型窄跳过**以零成本挡掉。

**所以选 6 小时**。真正的省钱杠杆不是兜底间隔，而是**轮次阈值**（N=15 → 20 就把每次提取的钱省下 25%）和事务型跳过。


## 1. 我读到的你的方案（回述，先对齐）

1. **触发**：① 每 N 轮左右对话提取一次（N 可配、默认 15；redis 里存的对话轮次也用同一个数）；② 没攒够 N 轮但有新消息、且超过一定时间（半天/一天，待定）→ 也提取；③ 没有新消息 → 不触发。
2. **上下文重叠**：每次提取的 N 轮里，**前 K 轮是上次已经提取过的**（K = N × 0.3，系数可配），只作上下文，并在提示词里明确"这些轮次不要再提取"。
3. **会变的信息要记**：提取不只是新增，还包括**修改/补全**已有记忆。
4. **不再给 agent 前台写记忆的工具**（怕它乱改；而且后台一定会触发，redis 里有最近 N 轮，不需要实时）；只给一个**只读**工具：查询最近几次提取。
5. **写入前做矛盾检查**：用向量找到相关旧记忆 → 矛盾则以**最新轮次**为准 → 修改或删除旧记忆；粒度要求是"**只改相关部分，不动无关内容**"；如果旧记忆只有这一件事，就"删旧 + 写新"。
6. **存储**：这块记忆写入 **pgsql 的向量库**，接 embedding 模型；因此记忆模块要引入 **LangChain4j 的向量检索类**。
7. **其他层（core/work）暂不变**，但你感觉要变，让我给建议。

## 2. 三个必须先定的架构问题（我的建议）

### 2.1 向量库放哪：pgsql+pgvector，还是先在 MySQL 里做？

**事实**：自建 `mysql:8.0.46` **没有** `VECTOR` 类型/向量索引（阿里云 RDS MySQL、AliSQL 有，但我们跑的是社区版镜像）；`pgvector` 是 LangChain4j 的一等公民（`PgVectorEmbeddingStore`）。

**规模算一下**：现在活跃记忆 ≈ 25 core + 28 work ≈ 50 条。就算涨到 **5000 条 × 1024 维 float**，全量在内存里算 cosine ≈ 20MB、单次查询 < 10ms。也就是说**在可预见的规模内，向量索引并不是瓶颈**。

**我的建议（推荐 A）**
- **A. 先抽接口 + MySQL 存向量 + 应用内 cosine**：新增 `MemoryVectorStore` 接口（`upsert / search / delete / rebuild`），实现先用一张 MySQL 表（`memory_vector(memory_id, model, dim, vec blob, text_hash)`）+ 启动时加载进内存做点积。**换 pgvector 时只换实现**，业务代码零改动。
- **B. 现在就上 pgsql + pgvector**：多一个容器、一个数据卷、一套口令、一份备份、一个迁移目录、一份连接池配置。功能收益在 50~5000 条规模内**基本为零**，但运维面翻倍。

**为什么我倾向 A 而不是直接上 B**：这个项目的**第一优先级是"用户长期记忆不丢失"**，现在记忆只有一套 MySQL + 每日 zip 备份这一条命。多一套库 = 多一个会丢/会忘备份的地方。等真的到万级或要多用户隔离，再切 pgvector（接口已经抽好，成本可控）。

### 2.2 embedding 从哪来（这是新增依赖，必须先定）

**DeepSeek 没有 embedding 接口**（[DeepSeek-V3 issue #806](https://github.com/deepseek-ai/DeepSeek-V3/issues/806)：官方明确没有 dedicated embedding）。所以必须接一家：

| 选择 | 说明 | 备注 |
|---|---|---|
| **阿里云百炼 `text-embedding-v4`（推荐）** | 你已经在阿里云（ECS/域名/解析），同账号开通、国内直连、便宜（约 0.0005 元/千 token 级） | 需新增一个 key（只放服务器 `.env`） |
| 智谱 / 硅基流动（BGE-M3） | 也便宜 | 多一家供应商 |
| 本地 ONNX（BGE-small-zh） | 零外部依赖、零调用费 | 要进镜像、占内存、效果略弱，可作**降级兜底** |

**成本**：每次写入 ~几百 token（提取出的几条事实）+ 每次检索 1 个 query（~50 token），按每天十几次算，**每月不到 1 分钱**——成本可忽略；**真正要设计的是"provider 挂了怎么办"**：embedding 失败时**必须降级回现在这条纯字面/关键词路径**，不能因为向量服务不可用导致记忆写不进去。

### 2.3 一条记忆的粒度：你纠结的"数学 + 教室放一起会不会影响向量"

**会**。向量是"整条文本的语义平均"：`第一周周二晚上课程为数学` 和 `第一周周二晚上课程教室在303` 各成一条时，检索"教室303"只命中后者、分数高；合并成一条时两者都能命中，但**分数被稀释**（条数少时无所谓，上千条后 top-k 容易漏）。

所以业界有两条路：
- **原子事实**（Mem0 默认）：一条一句 subject-predicate-object。检索准、更新单点；缺点是同一实体的 n 个属性散在 n 条里，注入上下文时要自己聚合。
- **实体卡片**（Graphiti/Zep 的 entity + edges；本项目"块"的形态）：一个实体一条卡片，属性是字段/多行。

**我的建议：实体卡片 + 一行多向量**（两全，且正好实现你要的"只改相关部分"）：

```
memory_card: id=1  subject="第一周·周二晚·数学课"  attrs={时间:周二9-10节, 教室:303, 教师:—}
memory_vector: (card=1, kind=SUBJECT, text="第一周周二晚数学课")
               (card=1, kind=ATTR,    text="第一周周二晚数学课 教室 303")
               (card=1, kind=ATTR,    text="第一周周二晚数学课 时间 周二9-10节")
```
- 检索"教室303" → 命中 `ATTR` 向量 → 取回**整张卡片** → LLM 判定是"补充"→ **只改 `教室` 字段**，`时间` 不动（正是你要的"不得修改不相关内容"）。
- 不存在"两件事塞一句话导致检索变糊"，也不存在"拆成两条后数学和教室失去关联、换教室时找不到该改哪条"。

### 2.3 定稿：**存原子事实、注入时按 subject 聚合**（用户 2026-09-17 选"一条一句事实"）

既然粒度定为"一条一句事实"，你担心的"只改相关部分"反而**天然成立**——每个属性本来就是独立一行，改教室不会碰到时间。代价是"同一实体的多个属性散在多行、注入时要聚合"，所以定稿是两边取长：

```
memory_fact: id=1  subject="第一周·周二晚·数学课"  predicate="时间"  object="周二9-10节"  content="第一周周二晚数学课的时间是周二9-10节"
             id=2  subject="第一周·周二晚·数学课"  predicate="教室"  object="303"        content="第一周周二晚数学课的教室是303"
memory_vector: 每条 content 一份向量（subject 一起进文本，保证"数学课"这个锚在）
```

| 环节 | 做法 |
|---|---|
| 存储 | **一行一个事实**（subject / predicate / object / content）——检索准、更新单点 |
| 更新 | 命中旧行后按 **`subject + predicate`** 定位：新值覆盖 `object`，旧值写 `memory_change_log`（留痕、可回滚）；**不相关的 predicate 行完全不动** |
| 注入 | 取回后**按 subject 聚合成"卡片视角"**再进提示词（`第一周周二晚数学课：时间=…；教室=…`）——模型看到的是完整实体，库里存的是原子事实 |
| 过时 | 整条不再成立的 → `SUPERSEDED`（不删行）+ 视需要新增 |

这样：**存的是 Mem0 式的原子事实，读的是卡片式的聚合视图**，"换教室只改教室那条"和"回答时能看到完整课程信息"两件事同时成立。

## 3. 提取触发（你的①②③，落成可实现的设计）

现状：**时间驱动**（每轮后起 180 秒静默窗口、最长拖 300 秒、两次至少隔 180 秒）+ 今天刚上的"事务型窄跳过"。

改成**轮次驱动 + 时间兜底**：

| 条件 | 判据（可配置） | 实现 |
|---|---|---|
| ① 攒够轮次 | 自**上次提取**以来新增 **user 轮** ≥ `N`（默认 15） | 水位线取 `memory_extraction_run` 最后一行的 `created_at`（今天刚加的表，天然可用），数 `conversation_memory` 里之后的 user 行；或 Redis 计数器（重启即丢，不如查库可靠） |
| ② 时间兜底 | 有新消息 且 距上次提取 > `T`（建议 **12 小时**） | 现有调度器保留，只把"静默窗口"换成"T 的兜底" |
| ③ 没新消息 | 不触发 | 现状已满足（没有新消息就不会排队） |
| ④（建议加）显式要求 | 本轮出现 `记住/记一下/以后都` | 立即触发一次（**这是调度层的规则，不是工具**，所以仍然"不用给它前台工具"，但你让它记的东西不用等半天） |

**上下文重叠**：提取时把"上次窗口尾部 K 轮"（K = ceil(N × 0.3)，默认 5）放在提示词的【仅供理解上下文，**不要从这一段提取**】区块里，并给每轮标号（`[旧#1]…[新#15]`），让模型只从【本次新增】提取。

**注意**：现在的"事务型窄跳过"要继续保留——轮次驱动的代价是"每 15 轮必花一次"，而其中可能整段都是问课表/设提醒。

## 4. 写入路径：矛盾 / 补充 / 无关 三分类

```
候选事实 → embedding → 向量召回 top-k（k=6） → LLM 三分类（+ 输出改完的完整卡片）
   ├─ 无关     → 新建卡片
   ├─ 补充     → 只改命中的那个属性字段（其余原样）
   ├─ 矛盾     → 以最新轮次为准：改该属性；并把旧值写进 memory_change_log（留痕、可回滚）
   └─ 整条过时 → 旧卡片置 SUPERSEDED（不删行）+ 新建卡片
```
和现状的关系：现在的 `MemoryTextSimilarity`（字面 ≥0.72 直接替换）+ `reconcileCoreWithModel()`（第二次小调用判"换了说法"）**就是这套的简化版**，v2 只是把"字面召回"换成"向量召回"、把"整条替换"换成"按属性改"。

**成本控制**：第二步 LLM 判定**只在向量召回到"可能相关"（分数过阈值）时才调**；召回为空就直接新建，不花第二次调用。

## 5. 撤销规则 12（"会变信息不记"）+ 两套真相的处理

**规则 12 撤销已确认**（2026-09-17）：会变的信息**要记**，但必须和"按属性改 + 旧值留痕 + 过时作废"**同批上线**。

- **反例就在库里**：`晚上上课地点是8B304.305，必须记住` 这条错的教室号至今还是 ACTIVE——它就是"**记了会变的信息 + 没有可靠的更新机制**"的产物。所以"要记"必须配"能改、能作废、有版本"，否则新版只会比现在更脏。
- 因此 §3/§4 的"按 `subject+predicate` 改 + 留痕 + `SUPERSEDED`"**不是可选项**，是和"记会变信息"绑在一起的前提。

### 5.1 图片/文件与记忆的关系（用户 2026-09-17 定调）：**基线 + 补丁，不是覆盖**

用户的原话要点：**"图片/文件的事实不是被用户覆盖——不是用户说一句就直接不看图片了，而是在此基础上根据用户的话修改。"**

所以不是"优先级替换"，而是**字段级的基线 + 补丁**：

| 概念 | 含义 |
|---|---|
| **基线值**（`source=DOC`） | 从图片/文件抽出的事实（可能不全、可能过期）。**永远保留**，不被抹掉 |
| **补丁值**（`source=USER`） | 用户后来的补充/纠正（"教室其实是 303"）。**只改命中 `subject+predicate` 的那个字段** |
| 当前值 | 有补丁取补丁，否则取基线；**两个值都留在库里**（`memory_change_log` 记 before → after） |
| 回答时 | 可以如实说"课表图上写的是 7B-301，你后来补充是 303，我按 303 答"——**依据可追溯**，不是把图片忘掉 |
| `AUTO`（模型从对话推断） | 最低一档：只在有明确依据时记，出现分歧时让位给 DOC/USER |

所以图片/文件**始终是基础信息**，用户的话是**在此之上的修正**；DOC 与 USER 不是二选一，而是"基线 + 补丁"两层摆在同一张事实表里。

**需要松一格规则 13**：原来"从图片看出来的事实一律不进记忆"要改成"**可以进，标 `DOC`，允许被用户的话按字段修正**"——否则"图片是基础信息"落不了地（图片内容永远进不到记忆检索里，就是今天上午"改课表只能改图片文字"的窘境）。


## 6. 只读工具（你明确要的那个）

`recentExtractions(limit)`：返回"最近几次提取"的摘要——时间、读了多少轮、写了几条、改了什么（before → after）、为什么空。**数据源就是今天刚上线的 `memory_extraction_run` + `memory_change_log`**，等于把面板「记忆」页签搬进对话，不用新表。它是只读的，不碰写入路径。

## 7. 其他层记忆（core / work）的建议

- **core 记忆**（稳定身份/偏好/底线，现在 25 条）：**不需要向量**——它本来就要全量注入，条数少。要做的是**冲突合并**（同一件事的多条合成一条），这正是 v2 的"卡片 + 按属性改"能顺手解决的。
- **work 记忆**（有期限的任务，现在 28 条）：现在靠 `validUntil` + FSRS 复查。建议把"到期/完成"做成**显式状态机**（ACTIVE → DONE/EXPIRED → 归档），v2 之后**会变的事实**（课表/日程）单独一层 `FACT`（带 `valid_from/valid_to` + `superseded_by`），检索时只注入"当前有效"的。
- 一句话：**core = 不变的人**，**work = 在做的事**，**fact = 会变的现实**（v2 新层）。三层各自的有效期与注入策略不同，别混在一张表里。

## 8. 分阶段实施（每步独立可验证、可回滚）

| 步 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **1** | 触发改成"轮次驱动 + 12 小时兜底 + 上下文重叠 + 显式要求立即触发"；保留事务型窄跳过 | 无（用现有审计表做水位线） | 低（只改调度与提示词） |
| **2** | 卡片模型 + 按属性改 + 旧值留痕 + `FACT` 层；**先用现有字面相似度**做召回 | 迁移 V11 | 中（改存量结构，但可并行双写） |
| **3** | 引入 embedding + `MemoryVectorStore` 接口 + MySQL 实现（应用内 cosine）+ 失败降级 | 需要 embedding key | 中（外部依赖，必须能降级） |
| **4** | 召回换成向量 + LLM 三分类（§4） | 步 3 | 中（多一次调用，要控成本） |
| **5** | 只读工具 `recentExtractions`；core 冲突合并；两套真相同步（§5） | — | 低 |

**每一步都能单独上线**：步 1 立刻省钱且上下文更全；步 2~4 才是"会变信息"和向量；步 5 是收尾。

| 检索延迟 | 字面匹配 <1ms | 应用内 cosine（5000 条）<10ms；外部 embedding 调用 ~100~300ms（**只在提取时**，不阻塞对话） |

## 10. 风险与回滚（我的自评）

1. **最大的风险不是技术，是"记忆是唯一命"**：任何动存量结构的步骤都要 ① 先 `mysqldump` ② 旧行不删只改状态 ③ 有回滚脚本。参照坑 58/63 的做法。
2. **两套真相**（课表同时在资料库和记忆里）→ 必须二选一（§5）。
3. **embedding 供应商不可用** → 必须有降级路径（退回字面/关键词），并且**降级时不能写脏数据**（宁可这次只新增、不做合并）。
4. **"会变信息"放开后**，库会变脏的唯一解是"更新机制真的被用起来"——所以步 2 上线后**必须先在面板上盯一周**：每周看 `MEMORY` 页签的"矛盾/补充/新建"比例，比例失衡（比如全是新建）说明更新路径没生效。
5. **不做**：不删掉后台提取（前台工具化仍不采纳，理由见坑 27）；不把 core/work 与 fact 混成一张表；不在没有降级路径时把向量检索设成唯一路径。

### 12.3 写死在程序里的规则（不靠模型自觉）

1. **按 `subject + predicate` 定位更新**：精确匹配优先；匹配不到再用字面相似度 ≥0.72 触发**第二次小调用**判"是不是同一个 subject"（复用 `reconcileCoreWithModel` 的路子）。
2. **只改命中字段**：一行一事实，天然满足"不得修改不相关内容"。
3. **DOC 不被抹掉**（按你的澄清）：用户的话是**补丁**；基线行保留，`memory_change_log` 记 before → after，回答时可回溯"图上写的是 X，你后来补充 Y"。
4. **作废不删行**：整条不再成立 → `status=SUPERSEDED` + `superseded_by` 指向新行。
5. **降级**：`MemoryFactIndex` 抛异常或不可用时 → **只新增、不合并**（宁可多一条，也不猜着改）。
6. **开关**：`MEMORY_FACT_ENABLED`（默认 true）；关掉后提取器不产出 facts、注入不加事实段，行为回到今天。

### 14.3 顺手修掉的一个**会让事实层完全失效**的坑

改法：`CLASSROOM_TOPIC`（话题词）与 `ASKING`（`？/吗/在哪/几点/哪个…`）**同时命中**才算事务型——**提问才跳过，陈述照跑**。

### 14.4 关键设计（写死在程序里，不靠模型自觉）

1. **关系判定交给模型，动作由程序执行**：模型只输出 `{id, relation, reason}`，`SUPERSEDE` 的落库动作（置状态、写 `superseded_by`/`valid_to`、留痕）全在 Java 里；模型判不出来 = 按"无关"新增（保守，不丢信息）。
2. **DOC 基线不因用户补丁下线**：目标行是 `DOC`、新值不是 `DOC` 时，基线行保持 ACTIVE，只在 `memory_change_log` 记 before→after。这样"图上写 402、你后来说 405"两句话都还在。
3. **同值不新增**（SAME → `CONFIRM` 只刷 `updated_at`/`confidence`）：实测第二次提取把已有两条事实又吐了一遍，结果只新增 0 条、两条 CONFIRM——**重复提取不会把库撑大**。
4. **向量自愈**：api-key 是后填的，之前入库的事实没有向量就**永远召回不到**（表现为"改教室改不动"）→ 每次 `apply` 顺手补一小批（20 条），面板 overview 的"缺向量 M 条"会自己回落到 0。

## 15. 触发改造（v2 步 1，2026-09-18，已本地端到端验证）

旧机制是"静默窗口"（每轮后开 180 秒窗口、新消息就重置、最多拖 300 秒）。实测两个毛病：
**① 一场连续对话里跑很多次**（1.5 小时 13 次、0.13~0.19 元，约一半是空转）；
**② 窗口边界会切在话说到一半的地方**（"那改成 305 吧"被切到下一窗，模型不知道在改哪件事）。

### 15.1 现在的触发条件（任一满足就排一次）

| 条件 | 配置键 | 默认 | 说明 |
|---|---|---|---|
| 轮次 | `MEMORY_EXTRACTION_ROUNDS` | 15 | 上次提取之后机主又说了 15 条 → 跑 |
| 时间兜底 | `MEMORY_EXTRACTION_MAX_IDLE_HOURS` | 6 | 待提取窗口里**最早那条**放了 6 小时 → 跑（"聊两句就安静了"的记忆不会一直不进库） |

（原先还有第三个条件"用户说「记住」就立刻跑"，**2026-09-18 用户明确要求删掉**：不要这种特例。）

到点后再等 `MEMORY_EXTRACTION_COALESCE_SECONDS`（默认 10）合并同一串消息；
`MEMORY_EXTRACTION_MIN_INTERVAL_SECONDS`（默认 180）仍是硬底线。

**轮次计数放在 Redis**（`memory:pending:<user>`，用户 2026-09-18 提的：更快、不压库）：
每来一条消息 +1，**提取真跑完就置 0**（不是删键——置 0 让下一条直接 `INCR`，省掉一次回退查库；
而"键被清空"是**消失**不是 0，自愈不受影响）。`0 → 1` 那一步要把"最早一条"的时间戳写回去，
否则"拖了 6 小时就跑一次"会因为拿不到最早时间而永远不触发。
**键不在时不能直接 `INCR`**——那会把键从 1 建出来，"按库里真实条数兜底"就永远走不到；
现在键不在就先查库、按真实条数种回去（这条消息已经落库，所以不用再加 1）。
"计数 >0 但时间戳丢了"同样回退查库。

实测：手动删键 → 下一条消息日志 `轮次计数不在 Redis（首次或已被清空），按库里真实条数种回 待处理=2 条` → 正常触发；
手动提取跑完 → `pending=0`、`since` 已删 → 再发一条 → `pending=1` 且时间戳补回；
把计数改成 999 并删掉时间戳 → 再发一条 → **回退查库得到真实的 2**（不是 1000）。

**窗口行数跟着 ROUNDS 自动推导**（2026-09-18 用户指出"不该写死 40"）：

```
窗口 = (ROUNDS + 重叠) × 2 行
重叠 = min(overlap-turns 上限, ⌈ROUNDS×0.3⌉)      # 上限默认 5 轮，用户 2026-09-18 加的约束
```

- 15 轮 → 重叠 min(5, 5) = 5 → **40 行**（正好是原来那个数）；30 轮 → 重叠仍 **5**（被上限封住）→ 70 行。
- 写死的坏处很实在：把 ROUNDS 调到 25、窗口还是 40 行时，**触发它的那 25 条里最老的 5 条会落在窗口外、静默漏记**。
- 新消息比它多时继续放大：`max(推导值, 新条数×2+10)`，上限由 `memory.conversation-extraction-limit`（默认 80 行）兜住。
- 想手工钉死：`MEMORY_EXTRACTION_WINDOW_ROWS`（默认 0 = 自动推导）。

**坑（我第一次就踩了）**：不能拿 `extraction-recent-turns=0` 当"自动"的哨兵——那个值会走
`MemoryPolicyProperties` 的覆盖逻辑、被 `Math.max(1, …)` 夹成 1，日志里会看到 `窗口=…/10`。
所以另开了一个键 `extraction-window-rows`，`extraction-recent-turns` 退回它本来的用途
（读不到库时去 redis 兜底读窗口）。

实测：`ROUNDS=30` → `窗口=6/70`；`ROUNDS=15` → `窗口=6/40`；`ROUNDS=3` → `窗口=6/16`
（推导值 8，但"新条数×2+10"的下限 16 更大，取 16）。

**前置过滤整块删除**（2026-09-18 用户要求"不该用硬编码正则替模型决定"）：
原来那道 `transactional-only`（整窗新消息全是"问课表/设提醒/元问题/纯语气词"就跳过）连规则带开关一起删了，
**该不该记全交给模型判断**。它已经咬过一次——"教室/课表/第.周"整类被它当事务型跳过，正好把要记的事实挡在门外。
代价是"整窗都在问课表"这种轮次也会真跑一次模型（约 0.05 元/次）；嫌贵就调大 ROUNDS，而不是把正则加回来。
只剩 `WINDOW_EMPTY`（没有可读轮次）会跳过——那是事实，不是启发式。
实测：故意连发三条"问课表 / 设提醒 / 你刚记录了什么"（旧版必然整窗跳过），现在照跑，
审计 `skip_reason` 为空、还真的写出了 1 条事实。

### 15.1.1 两个"静默失效"的坑（2026-09-18 实测挖出来）

1. **思考 token 吃满上限**：结构化档原来 4096。窗口变大后实测一次提取
   `completion_tokens=4505`、其中 `reasoning_tokens=3769` → **4096 会把正文截断**，
   JSON 解析失败、这一趟白跑（花了 0.018 元什么都没记）。已把 `LLM_MAX_TOKENS_STRUCTURED`
   提到 **16384**（上限不计费，放宽没有额外成本）。这就是当年反思整条作废的同一个坑（坑 60），
   区别是提取失败看起来像"这轮没什么值得记的"，更难发现。
2. **解析失败被当成"跑完了"**：原来 `parse()` 失败返回空结果，审计里 `skip_reason` 为空
   （与"正常跑完但没东西可记"无法区分），而且**这段对话会被当作已处理**（计数清零 → 再也不提取）。
   现在解析失败：日志明确写 `记忆提取结果解析失败（本次不算已处理）`、
   审计记 `PARSE_FAILED`（面板显示"模型输出没解析出来（多半是思考把额度吃满）"）、
   返回 false 走失败重试（重试仍失败则保留计数，下轮继续）。

### 15.2 三个"不小心就会写错"的地方（都踩过并已修）

1. **轮次要存在库里，不能在内存里记计数器**：这个应用**每次部署都重启**，内存计数器反复清零 →
   "攒够 15 轮"可能永远到不了，记忆提取等于停摆。现在放 Redis（见 §15.1），
   Redis 里没有就回退按 `conversation_memory` 算（两条 `@Query` 计数）。
2. **边界要用提取的"开始"时刻，且 FAILED/STALE/PARSE_FAILED 不能算数**：
   - 用结束时刻当边界 → 提取跑的那十几秒里用户说的话（不在这一趟窗口里、时间上又早于结束时刻）**永远轮不到提取**；
     现在用 `createdAt - durationMs` 当边界。
   - `FAILED` / `STALE`（跑到一半窗口变了、结果被丢弃）/ `PARSE_FAILED` 都没真正处理过那段对话，
     算作边界就等于把它们悄悄放过去。
3. **不能再在每轮开头 `cancelPending`**：`AgentOrchestrator` 原来每轮都取消挂起的提取（旧"窗口重置"语义），
   在轮次驱动下有两个坏结果：① 排队中的提取被用户自己刚说的话取消；② 排在队里的提取会被紧跟的第二条消息取消。
   现在不取消；另外**提取正在跑的时候不改代号**（改了会让这趟被判"过期"，白花一次调用还不写回），
   跑完再看一眼窗口满不满，满了立刻再排。

### 15.3 上下文重叠（K=5，前 K 轮只作背景）

窗口取最近 `MEMORY_EXTRACTION_RECENT_TURNS`（**默认从 20 改到 40**：15 轮 ≈ 30 行，给 20 行根本装不下，
最老的几条会被挤出窗口），其中**最老的 `MEMORY_EXTRACTION_OVERLAP_TURNS`（默认 5）条机主消息**
在提示词里标成 `user[背景/上次已处理]`，并加了规则 14：只用来理解上下文，不要只凭它们新建记忆。

标几条不是拍脑袋：按"这一窗真正新增了几条"算（`burstTexts` 是上次提取之后用户说过的话）——
窗口里 20 条、其中 15 条是新的 → 最老 5 条标背景。
**首次提取（没有 burst 信息）一条都不标**：那时候没有任何"上次已处理"，标了就等于把最老的几条永久漏掉。

## 16. 提取从"1 次主调用 + N 次小调用"改成"一次调用定稿"（2026-09-18，已实测）

用户问"触发提取时是只调一次文本模型吗、输出包含本次要加的所有记忆吗"——查完发现：
**输出确实包含全部内容，但写入时会为每条事实再叫一次模型判关系**。实测那次（4 条事实）：
主调用 prompt 5319 / completion 10923（思考 9853）、小调用 4 次合计 prompt 1594 / completion 3253
→ 小调用多花 **0.0146 元 + 15 秒**（主调用 0.0490 元，小调用占 30%）。

### 16.1 为什么原来必须后置

合并判定要知道"新事实跟哪条已有事实像"，而"像不像"要算新事实的向量，而新事实的文本是**主调用刚生成的**
——顺序上只能"先主调用 → 再向量召回 → 再叫一次模型判关系"。

### 16.2 现在的做法（混合）

**当前有效事实卡片 ≤ 30 张**（`memory.fact-prompt-cards`）且渲染 ≤ 4000 字（`...-max-chars`）时：
把卡片清单**直接放进主提示词**（`· 第一周·周二晚·数学课：教室 303；教师 王老师`），并加规则 15 要求模型
在输出每条 facts 时**顺便给出** `relation`（NEW / SUPERSEDES / SUPPLEMENT / SAME）和 `targetSubject`
（逐字照抄卡片里冒号前的名字）→ **一次调用定稿**，不再召回、不再小调用。

**超过上限**（事实多了）→ 不带清单，并把模型给的 relation/targetSubject 全部清掉
（它看不到已有事实，那些字段不可信），退回原来的"向量召回 + 小判定"——硬塞必然截断，
截断就可能漏掉该合并的那条，这比多花几分钱糟得多。

写回按模型给的结论执行（`MemoryFactService.writeWithDecision`）：定位合并目标用
`targetSubject + predicate` **精确查槽**（不用向量、不用 id，因为清单里给的就是这些名字）；
SAME → 只刷新、不新增；SUPERSEDES → 插新行 + 把旧行标 SUPERSEDED；SUPPLEMENT → 沿用目标卡的
subject **原始拼法**（免得同一件事两种写法各成一张卡）后新增；找不到目标 → 保守当新建。

### 16.3 向量"算几次、什么时候算"（用户 2026-09-18 追问的点）

- **召回那次算的向量对应的是"模型刚吐出来的文本"，而入库的文本可能已被收敛**（沿用了已有卡片的 subject）。
  所以现在把落库结构改成：**先定稿 subject/predicate/content → 插行 → 再按最终 content 只算一次向量**
  （`persist()` 的最后一步）。避免"向量和内容对不上"。
- 走卡片路径时**连召回都不做**，写一条事实就是**一次 embedding**（原来同一条文本要算两次：
  一次召回、一次存向量）。
- **旧行被取代不重算向量**：行不动、向量不动，召回只查 `status='ACTIVE'`，旧向量不会再被用到。
- `reindexMissing()` 的自愈仍在（按 content 补算），用于"api-key 是后填的"那种历史欠账。

### 16.4 实测（本地，rehearsal pg + 假向量服务，真 DeepSeek）

| 场景 | 结果 |
|---|---|
| 第 1 次提取（当时还没有任何卡片 → 不带清单） | 走老路；2 条事实 `依据=新增`；同批第 2 条触发 1 次小调用（首轮一次性，可忽略） |
| 第 2 次：`第一周周二晚数学课的教室改成506了，另外这门课是周三交作业` | **1 次调用**（prompt 1577 / completion 1268）；`303 → SUPERSEDED(26)`、`506 ACTIVE`、`教师` 不动；`交作业时间=周三` 新增；日志 `依据=主调用判定：同一属性被改写` |
| 第 3 次：`周二晚上数学课的老师换成李老师了`（**换了说法、没提"第一周"**） | **1 次调用**；落库 subject 仍是 `第一周·周二晚·数学课`（照抄了卡片名）；`王老师 → SUPERSEDED(28)`、`李老师 ACTIVE` |

## 17. 归档机制整块删除（2026-09-18，用户决定；已上线）
